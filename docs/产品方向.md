# Structify 产品差异化与演进方向

记录日期：2026-10-25。

状态：本轮讨论形成的产品方向与候选阶段划分，尚未实施。本文不替代正式设计、开发计划或验收记录；各阶段进入开发前仍需明确接口、数据模型、范围及测试。

## 1. 产品定位

以现有 AI 课堂为入口，建设能观察学生操作、验证学习结果、按错误补讲的数据结构学习平台。

面向学生的价值可以表达为：同一个知识点，能讲、能演示、能动手验证；哪里没掌握，下一步教学就针对哪里。

现阶段优先回答：学生在本课程中卡住后，Structify 能否帮助他理解原因，并独立完成一道不同的题目。课程生成、多角色或展示形式本身不作为差异化成立的证据。

课程生成继续保留，其职责逐步明确为：基于已有课程材料和学生当前表现，组织这一次该怎么教。默认学习路径可由教师审核；模型围绕学生卡点调整解释、例子和提示。确定性动画、服务器规则及测试用例负责可执行部分的验证。

## 2. 依据与证据边界

本方向基于本轮对本地仓库的静态核查，以及此前对产品功能的讨论。没有在本轮启动服务、重跑测试、验证线上部署或进行真实学生实验。

- 当前学习室实现状态以 [studyroom 架构](architecture/studyroom.md)及实际调用链为准。
- 历史文档存在回滚和后续变化，历史通过不代表当前再次通过。
- 源码存在不等于线上已经启用，也不证明课程素材覆盖、讲解质量或学习收益。
- 课程资源和题库的外部配置、审核状态及覆盖范围仍需独立核实。
- 下列“缺口”属于产品与调用链判断；不能把尚未核对的全链路连接写为已完成。

## 3. 现有能力与下一步缺口

### 3.1 课程生成：保留可靠的片段生成底座

架构已描述大纲审核、冻结片段、有限准备、校验后发布，以及后续准备失败时保留已发布内容的边界。现有修订、租约、幂等、预算和计费能力应继续复用。

这些主要解决课程如何可靠地产出。下一步需要把生成内容与具体学习目标、学生行动及验证结果连接起来。

依据：[当前学习室架构](architecture/studyroom.md)。

### 3.2 课堂：从组织材料走向组织学生行动

PPT、确定性动画、C 示例和讲解已进入同一课堂；存在材料切换、顺序讲解及定位能力。

下一步围绕同一任务串联预测、运行、反馈和迁移验证。例如链表删除动画结束前，先让学生判断指针变化，再进入代码修改，而不是单纯切换下一份材料。

依据：[StudyroomSceneStage.vue](../frontend/src/user/components/studyroom/StudyroomSceneStage.vue)。

### 3.3 动画：已有参数化与确定性轨迹基础

能力目录中存在初始数据、位置、插入值等参数；课堂通过动画规划接口获取动画与轨迹。因此不应把现有能力简单归为只能播放的固定动画。

下一步先对少量能力开放方便的输入修改、帧级预测和规则判定，并把当前帧纳入追问现场。需要继续核实各能力的实际支持程度。

算法仿真与学生 C 程序的真实执行属于不同事实来源，不能将两者直接视为同一状态。

依据：[动画能力目录](../backend/dsvp/engine/animation-capabilities.js)、[课堂场景实现](../frontend/src/user/components/studyroom/StudyroomSceneStage.vue)。

### 3.4 C 实验：优先接通实际运行代码与课堂追问

课堂代码组件支持编辑、输入和运行。独立代码分析服务已能使用源码、输入、输出或运行标识进行分析。

本轮读取的课堂追问上下文仅包含步骤、场景、资源标识、代码模式及输出，没有修改后的源码、输入或可信运行标识。追问服务又会提供绑定示例的源码，存在分析对象与学生实际运行代码不一致的风险。

下一步应将实际代码版本、输入和服务器运行快照绑定到课堂追问，复用既有分析能力。代码行高亮属于讲解定位，不等于真实单步调试。

依据：[课堂代码组件](../frontend/src/user/components/studyroom/StudyroomCodeScene.vue)、[追问上下文](../backend/spring/src/main/java/com/feng/dsagent/studyroom/StudyroomFollowUpContext.java)、[代码分析服务](../backend/spring/src/main/java/com/feng/dsagent/compiler/CodeAnalysisService.java)、[追问服务](../backend/spring/src/main/java/com/feng/dsagent/studyroom/StudyroomFollowUpService.java)。

### 3.5 小测：从判分走向可追溯的错因与再验证

已有服务端单选判分、尝试记录和题库选择实现。当前实现允许题库不足时生成补足题目，不能描述为全部来自审核题库。

下一步明确题目来源和版本追溯，给少量题目增加具体能力、错因标签，并在补讲后使用不同题目验证。判分机制的存在不证明题目及答案本身正确，题目质量仍需审核。

依据：[ClassroomCheckService.java](../backend/spring/src/main/java/com/feng/dsagent/studyroom/checks/ClassroomCheckService.java)、[ClassroomQuestionBank.java](../backend/spring/src/main/java/com/feng/dsagent/studyroom/checks/ClassroomQuestionBank.java)。

### 3.6 学习证据：复用事件和掌握度估计，核对实际连接

已有学习事件、进度和带置信度的掌握度估计。无需再从零建设一套大型知识图谱。

下一步追踪新课堂作答、代码实践和动画交互是否进入统一事件及其消费链，并区分程序运行成功、任务测试通过和独立迁移完成。不能因为模块存在就宣称学习闭环已经打通。

依据：[LearningEventService.java](../backend/spring/src/main/java/com/feng/dsagent/learning/LearningEventService.java)、[MasteryEstimator.java](../backend/spring/src/main/java/com/feng/dsagent/learning/MasteryEstimator.java)。

## 4. 候选演进阶段

以下顺序表达产品优先级，不构成工期承诺，所有阶段均为待实施。

### 第一阶段：让助教准确理解提问时的现场

范围：

- 代码绑定实际源码版本、输入和服务器运行快照。
- 动画绑定参数、轨迹标识和提问时的当前帧。
- 追问冻结现场；学生继续修改或切换材料不覆盖历史现场。
- 复用已有代码分析、课堂追问及材料定位动作。
- 运行记录的身份、权限和来源由服务器校验，客户端报告不作为权威运行证据。

验收条件：

- 学生修改示例并运行后，追问分析的是这次实际运行的版本。
- 后续修改不改变旧问题对应的源码与运行结果。
- 未运行的草稿与已运行版本能明确区分；没有执行证据时不虚构运行事实。
- 动画追问能对应确定的输入和帧，而不是只有动画资源名称。
- 扩展上下文后仍保留当前课程、片段修订、权限和预算边界。

### 第二阶段：完成一个“链表删除”学习任务

复用已有材料与能力，新增任务步骤、预测判定和代码测试之间的连接。

候选流程：

1. 使用课件和讲解说明前驱、待删节点及后继。
2. 动画暂停，让学生预测下一次指针变化。
3. 打开同一操作的 C 示例，补全或修改关键代码。
4. 使用确定性测试检查删除首个节点、末节点、唯一节点及无效位置。
5. 更换输入或删除条件，让学生独立完成迁移任务。

验收条件：

- 预测和代码任务由确定性规则、测试判定，模型负责解释和提示。
- 系统能分别记录看过、预测正确、代码通过任务测试及不同输入下独立完成。
- 采用明确的链表表示和边界约定，测试与讲解保持一致。
- 抽象动画状态不被表述为学生任意 C 程序的真实内存快照。

### 第三阶段：让错误改变下一步教学

先给单个任务定义少量能力与错误标签，例如：前驱定位错误、指针修改顺序错误、唯一节点删除后头指针处理错误、位置合法性检查遗漏。

错误发生后，系统定位已有讲解或动画，提供逐级提示，再用另一道题验证；必要时才调用模型生成补充讲解。避免因一道题答错而重新生成整门课程。

验收条件：

- 能追溯错误依据、提示次数、定位的材料、修改的代码版本和后续结果。
- 能完成“失败 → 针对性补讲 → 不同题目验证”的完整流程。
- 错因依据不足时保留不确定性，不把模型推测写成确定诊断。
- 新课堂证据实际进入学习事件及相关消费链。
- 阅读完成与掌握证据保持分离。

### 第四阶段：迁移到其他主题，验证教学价值

优先选择循环队列和树遍历，分别验证取模、空满边界，以及执行顺序、递归与状态预测。复用公共协议和组件，避免每章重新实现一套流程。

教师侧先展示聚合的常见错因、卡点步骤和典型边界问题，帮助调整教学。

验收条件：

- 学习任务协议和证据模型能跨主题复用。
- 记录首次独立完成、修复所需提示、不同题目通过及延迟复测结果。
- 学习收益通过真实试用和对照验证，不以观看时长、问答次数或生成数量替代。
- 根据实际失败位置决定后续投资，避免仅凭演示效果扩大范围。

## 5. C 内存可视化的投入条件

完整的任意 C 程序执行追踪暂不列为第一优先级。它涉及执行隔离、调试信息、内存追踪和未定义行为，范围明显大于指定算法动画。

当真实使用表明学生持续卡在自己程序的指针、内存变化，并且现有提示及任务反馈不能有效解决时，再设计受限追踪：优先指定结构和练习模板，逐步评估泛化范围。

实现难度本身不能证明产品价值。先验证一个学习任务，再决定是否扩大到通用调试器。

## 6. 首轮建议交付与明确边界

首轮建议交付两项：

1. 接通课堂中的真实代码运行上下文和动画当前状态。
2. 完成链表删除的预测、实践和验证流程。

保护既有工程边界：

- 保留已审大纲、冻结片段、有限准备和校验后发布的主链。
- 保留修订、运行隔离、租约、幂等、令牌计量和预算，不引入第二套生成链。
- 模型提出教学内容；服务器控制授权、资源绑定、权威状态及发布。
- 普通单元、集成和浏览器验证使用合成或公开样例，不执行付费模型评测。
- 不将私有课件、题库交付包、账号数据或运行数据库写入本方向文档及测试夹具。

## 7. 进入开发前需要明确的事项

- 链表删除任务采用的教材约定、示例、审核人和验收样例。
- 可信代码运行快照如何与课堂身份及源码版本绑定。
- 动画帧级状态与预测题如何定位及判定。
- 题目来源、版本、错因标签及替换题目的管理方式。
- 新课堂证据到学习记录、掌握度和后续推荐的实际连接。
- 小范围试用对象与评估方法；暂不预设未经验证的收益或工期。

这些事项在实施设计中逐项解决，不改变本轮“先接通现场，再验证一个任务”的优先级。
