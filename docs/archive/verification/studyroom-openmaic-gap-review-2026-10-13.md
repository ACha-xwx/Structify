# Studyroom 现状、OpenMAIC 差距与功能评价

审阅日期：2026-10-13。范围：当前 Structify Studyroom 实现、本次浏览器中的二叉树课堂，以及本地 `G:/Code/OpenMAIC` 代码。OpenMAIC 本地 HEAD 为 `2a98d02`（2026-10-07），不代表最新上游版本。

## 一、总体判断

**现在是“带学习路径和多资源展示的课程问答 MVP”，还不是“能驱动资源、连续讲课、被打断后恢复的 AI 课堂”。**

方向没有错，也不需要推倒重来。课堂、步骤、对话、进度、资源引用和授权检查已有基础。但“资源存在”与“老师围绕资源真正讲清楚”之间，缺少教学动作与课堂运行层。

我们的目标不是照搬即时生成 PPT。采用已有 PPT、已有动画与 C 示例是合理的：材料更可控、便于课程审核，也减少生成成本。应学习 OpenMAIC 的场景模型和运行机制，而不是优先复制它的内容生成方式。

## 二、已经具备什么

### 1. 课堂后端：具备 MVP 基础

- 首问经过知识检索、候选资源收集、模型生成、结构校验和持久化，得到学习步骤。
- 首问图有失败分支和一次修复；追问图区分普通回答与补充步骤。
- 课堂记录包含初始问题、摘要、当前步骤和版本；步骤包含证据、资源、补充标识与父步骤；消息关联步骤。
- 有用户所有权校验、授权证据约束、资源白名单和模型配额，不是纯前端假对话。

评价：这些是值得保留的工程基础。当前 LangGraph4j 解决了“请求如何处理”，还没有解决“课堂如何运行”。数据库持久化课堂内容也不等于图任务可中断、恢复或重试。

依据：`backend/spring/src/main/java/com/feng/dsagent/studyroom/StudyroomGraph.java:155`、`:307`；`StudyroomRecords.java:13`。

### 2. 资源：有真实课件，但关联质量仍弱

- 已有 22 套原版 PPT 转换出的 1210 页 WebP；不是临时画的假 PPT。
- 索引提取了源 PPT 的标题和正文，图片访问走现有接口。
- 开发知识库为 10 个章节的少量模拟文本，不是完整教材知识库。
- 动画和 C 示例的开发替代资源存在，但覆盖的是部分主题、部分操作，不是所有算法。
- 当前生成的课件索引中，语义摘要、知识点、教学角色等为空；课时映射文件的 `lessons` 为空。

评价：素材数量已不是主要瓶颈，**资源可检索、可解释、可正确绑定**才是瓶颈。1210 页图片不等于 1210 页可编排的教学资源。

依据：`scripts/build-studyroom-presentation-index.ps1:196`；`presentation-materials/rendered/lesson-presentation-plans.json:4`；`backend/spring/src/main/resources/db/dev/R__seed_studyroom_mock_knowledge.sql:1`。

### 3. 前端：基本融合完成，仍是资源浏览器形态

- 有课堂标题、学习路径、当前步骤讲解、PPT/动画/C 三类平级入口和下方对话。
- 可以显示真实 PPT、播放动画帧、编辑 C 文本并发起运行请求。
- 有加载失败提示、资源切换竞态保护和步骤进度保存。
- 本步讲解和对话主要是纯文本；没有围绕课件区域、动画帧或代码行的讲解锚点。
- C 编辑器目前是 textarea，不能等同于带断点、变量观察、调试或评测的 IDE。

评价：布局与我们原先的融合目标一致，但三个资源仍是“用户自己切换的附件”，尚未成为老师讲课过程中自然切换的教学场景。

依据：`frontend/src/user/views/StudyroomView.vue:202`、`:209`、`:211`、`:219`。

## 三、目前最需要正视的问题

### 1. 演示资源还不是统一后端编排的结果

`/studyroom-demo` 调用真实课堂 API 后，前端 `attachMockResources` 根据章节和关键词补 PPT、动画、C 资源。`/studyroom` 不做这层补充。

这意味着演示页“看起来资源齐全”，不等于 AI 已经在后端选择、解释并保存了这些资源。前端新增资源不会成为后端课堂计划的一部分，追问模型也无法完整看到这些新增资源。

这是目前与“开发和上线用一套，仅资源模拟”要求最重要的偏差：业务 API 是真实的，但演示资源绑定仍有另一条前端路径。

此外，后端限定章节时的 PPT 候选依赖 `textbook/%` 知识来源及课时映射；开发知识来源是 `dev-mock/%`。当前没有真实教材映射时，章节课件可能不能进入后端候选。

建议：将模拟素材作为开发环境资源数据注册进统一资源目录；同一个后端绑定、验证、持久化过程处理真实与模拟资源。不要放开证据门禁，也不要通过生产逻辑特殊绕过授权。

依据：`frontend/src/user/views/StudyroomView.vue:43`；`frontend/src/user/studyroom-mock.ts:132`；`backend/spring/src/main/java/com/feng/dsagent/studyroom/StudyroomResourceCatalog.java:122`。

### 2. 追问复用的是课堂文字，不是完整教学上下文

追问会加载课堂标题、摘要、步骤文字和最近 20 条消息，但检索使用当前追问原文，没有先结合当前步骤和初始问题补全语义。已有授权证据也没有作为课堂证据集合直接复用。

因此“再举个例子”“为什么这样”这类自然追问存在检索不到证据而被拒绝的风险。应补全问题并重新校验可复用证据的权限，而不是降低检索阈值或取消授权要求。

当前步骤 ID 用于记录关联，但模型上下文没有明确完整的当前步骤资源、动画状态和学生代码状态，难以理解“图里这个结点”“这段代码第几行”等指代。

依据：`StudyroomGraph.java:186`、`:203`、`:225`。

### 3. 补充步骤是已有分支，不是稳定保证

是否补充依赖模型输出的 intent。补充结构校验失败会退化为普通回答，目前没有像首问那样的修复过程，也没有清晰告诉用户补充为何失败。

本次浏览器课堂有 11 步，用户要求“二叉树先序遍历的顺序是什么？详细展开。”后，页面回答只有一小段文字，末尾说“下面把这一顺序展开说明”，但当前消息没有实际展开内容。仅凭这个结果不能确认失败原因；它说明课堂体验没有兑现“详细展开”的承诺。

建议：明确普通回答、当前步骤补充、新增例题/资源的产品语义；让用户看到补充结果或失败原因，增加真实模型验收用例。

依据：`StudyroomGraph.java:265`；本次页面截图见第六节。

### 4. “图文搭配”尚未达到教学级联动

现在是上面放图、旁边/下面放文字。缺少“文字讲到哪里，课件重点在哪里；动画走到哪一帧，对应哪句解释；代码执行到哪一步，变量是什么”。

WebP 不会阻碍联动：可以在图片上叠加百分比坐标的高亮区域、箭头、标注。需要建立定位数据，而不是重新生成全部课件。

### 5. C 的闭环还没有完成

已有运行接口和页面入口，但当前环境曾验证为 `COMPILER_NOT_CONFIGURED`；本次审阅不把它算作已完成的真实运行能力。源码中该配置错误路径仍存在，运行环境是否变化需重新测试。

即便接通编译器，也还缺学生代码保存、执行结果解释、预期输出校验以及错误对应知识点。语法检查通过不能代替真实沙箱运行和教学反馈。

依据：`backend/spring/src/main/java/com/feng/dsagent/compiler/PistonCompilerGateway.java:70`。

## 四、OpenMAIC 真正领先的地方

### 1. 场景是统一教学单元

本地 OpenMAIC 的渲染器分发 `slide`、`quiz`、`interactive`、`pbl`。它不是把 PPT、动画、C IDE 硬编码成完全相同的三个标签；交互场景能承载实验，白板动作能承载代码展示。不能将这些自动等同于我们的 C 沙箱 IDE。

我们可以保持三类静态资源为主要场景，并预留题库类型，无需复刻它全部场景。

依据：`G:/Code/OpenMAIC/components/stage/scene-renderer.tsx:27`。

### 2. 场景内容与教学动作分离

OpenMAIC 除了生成大纲和场景内容，还生成场景 actions。动作包含讲述、聚光、高亮、激光指示、白板绘制/代码、讨论、交互组件状态等。

这才是从“展示资源”到“讲授资源”的关键。我们当前步骤只有 explanation 和 resources，没有可执行的教学动作序列。

依据：`G:/Code/OpenMAIC/lib/server/classroom-generation.ts:724`；`G:/Code/OpenMAIC/packages/@openmaic/dsl/src/action.ts:22`。

### 3. 课堂有运行状态和播放游标

OpenMAIC 的 PlaybackEngine 明确管理 idle、playing、paused、live 等状态，保存场景和动作位置，并处理讲课、暂停、讨论、打断与恢复。

我们目前保存的是当前学习步骤，不是“正在讲哪句话、指向哪个区域、动画进行到哪一帧”。动画播放器自身有播放状态，但它没有成为统一课堂状态的一部分。

依据：`G:/Code/OpenMAIC/lib/playback/engine.ts:1`。

### 4. Agent 的输出能驱动课堂

本地 OpenMAIC 使用 LangGraph 的 director → agent_generate 单轮拓扑，跨请求由客户端串行驱动讨论；单 Agent 时 director 甚至是代码逻辑，多 Agent 才使用模型选择发言者，并以流式事件交付结果。

因此不能简单说“它图节点更多所以更强”。**它更强的部分是状态、动作契约、前端执行器、讲课与讨论的协同。** 当前本地 `lib` 和 `packages` 搜索中，LangGraph 导入集中在 director-graph，而场景生成和播放并不是都用 LangGraph 实现。

我们已经有图，不建议继续为“图化”而图化。优先拆清规划、资源绑定、讲解生成、质量检查与运行状态职责，再决定哪些节点需要独立模型调用。

依据：`G:/Code/OpenMAIC/lib/orchestration/director-graph.ts:1`、`:485`。

## 五、对现有功能的评价

- **工程骨架：值得保留。** 授权、结构校验、所有权、数据库模型和真实模型调用是正确基础。
- **AI 大纲：能用，但教学质量尚未被证明。** 格式合法不代表难度、顺序、覆盖范围与材料匹配合适；需要教学目标、先修关系和质量用例。
- **PPT 展示：真实且实用。** 转换路径无需推翻，下一步应补语义、章节课时映射、区域锚点。
- **动画：有接入能力，但课堂联动弱。** 部分 mock 演示简短，不能将一个操作/少量帧等同于完整算法教学。
- **C 编辑器：入口阶段。** 能编辑、能请求运行，但不能宣传为已经完成代码实训闭环。
- **追问：课堂身份连续，语义连续性不足。** 当前资源和证据复用需要加强，补充行为也需要稳定验收。
- **UI：风格统一、功能清楚，但课堂感不足。** 用户仍要自己读步骤、选资源、读回答；缺统一讲课状态和视觉引导。
- **教学闭环：尚未形成。** 缺课堂内理解检查、练习反馈、错误诊断和掌握情况，不应仅用“点到第几步”表示学会了。

不提供百分比完成度或主观分数：目前没有完整用户测试、真实知识库评测或两套系统的同题教学实验来支撑数字。

## 七、建议推进顺序

### P0：先让已有承诺可靠

1. 开发资源数据接入统一目录：去掉“展示完成度依赖前端另行补资源”的架构偏差。
2. 追问基于当前步骤补全语义，复用仍有权限的课堂证据，保留原授权门禁。
3. 补充行为增加校验、失败解释和真实模型用例，避免“说要展开但没有展开”。
4. 接通安全 C 执行环境；未配置时明确显示状态，避免把请求按钮当成可用运行能力。

### P1：从问答升级为课堂

1. 统一步骤/场景契约：教学目标、主资源、辅助资源、讲解锚点、动作、来源。
2. 为一个二叉树案例先实现最小动作集：讲述、PPT 区域高亮、动画帧定位、代码行定位。
3. 增加课堂运行状态：准备、讲解、暂停、追问、补充、恢复；不要求第一版就有语音。
4. 资源计数与空态改为当前步骤语义；提供多个同类资源的选择入口，标明回答对应步骤。
5. 补真实知识库、课时映射与来源展示，验证讲解和资源内容一致。

### P2：教学闭环和体验增强

题库场景、代码输出评测、知识点掌握反馈、语音讲课、角色讨论与导出。题库是课程内检查，不等于必须先接入完整考试系统。多角色不是当前最高优先级。

## 八、下一阶段的验收标准

选“二叉树先序遍历”作为贯穿案例：

- 同一问题在普通入口和开发入口走同一个编排过程，差别只是资源数据来源。
- 课件、动画、代码使用一致的树和遍历顺序；缺匹配资源时明确降级，不能强配。
- 讲解指向实际课件区域、动画帧、代码行，而不只是并排呈现。
- “为什么先访问根”“再举个例子”无需重复完整主题即可在原课堂继续；授权仍有效。
- 要求细化后出现可见补充内容或明确失败反馈，原路径不被悄悄重写。
- 代码可真实执行，输出和例子一致，执行失败能解释。
- 刷新后课堂内容、补充资源和当前位置可恢复；之后再验收进程重启和持久数据库场景。

**结论：保留静态资源路线和现有后端骨架；下一步补统一资源绑定与课堂动作运行层，而不是先堆新 Agent、重做 PPT 或只模仿界面。**
